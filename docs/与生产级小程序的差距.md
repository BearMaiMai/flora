# 与生产级小程序存在的差距

> 当前版本：线上 1.0.0 | 评估时间：2026-07-07  
> 角色标签：🔧 后端 ｜ 📱 前端 ｜ 🤝 前后端配合 ｜ ⚙️ 运维/平台

---

## 一、安全类（高危，必须修）

### 1.1 数据操作缺 _openid 校验 🔧 后端
**位置**：`reminder/delete`、`reminder/update`、`reminder/complete`、`diary/delete`、`diary/update`

当前直接用 `.doc(id).get()` 不校验归属，用户猜中别人 ID 就能改/删别人的数据。

**修复**：所有写操作和单条读取操作前加 `.where({ _openid })` 校验。

### 1.2 云环境 ID 硬编码暴露 📱 前端
**位置**：`miniprogram/app.js`

源码里写了 `cloud1-d1gjubt747d28d4ac`，代码泄露会被利用。

**修复**：用条件编译或 env 变量注入，生产环境 ID 不提交到仓库。

## 二、运维类

### 2.1 没有数据备份 ⚙️ 运维
数据库没开自动备份，误删或 bug 导致数据损坏无法恢复。

**修复**：云开发控制台 → 数据库 → 备份设置 → 开启自动备份。

### 2.2 开发/生产共用同一环境 ⚙️ 运维 + 📱 前端
本地测试和线上真实用户共用 `cloud1-d1gju...`，本地改错了直接影响线上。

**修复**：创建第二个云环境，前端切换环境 ID。

### 2.3 没有异常监控 📱 前端主导
用户遇到 crash 或接口报错，开发者完全不知道，除非有人手动反馈。

**修复**：接入微信 We 分析（免费），监控线上报错。

### 2.4 没有 CI/CD ⚙️ 运维
云函数靠手动右键上传，每次改代码都要人工操作，容易漏传。

**修复**：用 `miniprogram-ci` + GitHub Actions，push 自动构建上传。

### 2.5 没有日志聚合 🔧 后端 + ⚙️ 运维
云函数日志散落在微信控制台，出问题要一个一个点开看。

**修复**：后端统一日志格式加 requestId，或接入日志服务。

---

## 三、性能类

### 3.1 限流器基于内存，分布式下失效 🔧 后端
`common/utils/rate-limit.js` 用 `Map()` 存计数，云函数多实例时各算各的。

**修复**：改用云开发自带的频控能力，或基于数据库计数表实现分布式限流。

### 3.2 数据库缺索引 ⚙️ 运维
高频查询（如 `reminders` 按 `_openid + nextRemindAt`、`diary` 按 `_openid + createdAt`）没建复合索引，数据多了查询越来越慢。

**修复**：在云开发控制台为高频查询字段建复合索引。

### 3.3 百科列表一次拉 200 条 🤝 前后端配合
`encyclopedia/index.js` 单次请求 200 条全量前端筛选，数据多了首次加载慢、内存占用大。

**修复**：后端已有分页接口，前端改成分页加载。

---

## 四、功能完整性

### 4.1 提醒只有云函数 push，没有微信订阅消息 🤝 前后端配合
云函数定时 push 只能更新数据库，用户收不到实际通知。微信要求订阅消息模板才能推送到用户手机。

**修复**：前端弹授权弹窗获取订阅权限，后端接入模板消息下发。

### 4.2 搜索只做本地过滤 📱 前端
百科搜索仅在前端内存中 filter，不能搜全部数据。

**修复**：接入已有的 `flower/search` 后端接口。

### 4.3 种植指南页仍用硬编码数据 📱 前端
`pages/guide/index.js` 和 `detail.js` 没有调用后端 `guide` 云函数。

**修复**：已有文档 `7.7前端待修改.md`。

---

## 五、工程规范

### 5.1 没有自动化测试 🔧 后端主导
改了云函数不知道会不会影响其他功能。

**修复**：至少为核心 action（login、reminder/complete、diary/update）加单元测试。

### 5.2 没有灰度发布机制 ⚙️ 运维
全量上线就是全量，没有分阶段观察的办法。

**修复**：微信后台用分阶段发布，先 5% 观察无 crash 再 100%。

### 5.3 没有版本回滚预案 ⚙️ 运维
线上 1.0.0 不能回退，如果有严重 bug 只能硬着头皮修。

**修复**：提交审核前在体验版上充分验证，准备热修复云函数的能力（云函数可独立更新不需要审核）。
